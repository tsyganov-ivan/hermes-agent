# MM-native-плагин как транспорт — схема транспорта

Статус: обсуждение дизайна (этап 1 — транспорт, этап 2 — протокол).
Что доказано/проверено в коде форка и доках Mattermost, что — гипотеза.

## Цель

Дать Hermes-ботам настоящие слэш-команды и интерактив (кнопки/меню/диалоги)
из Mattermost, включая мобильный клиент, **без внешнего HTTP входа в Hermes**
(Hermes остаётся за NAT).

## Установленные факты (проверено)

1. **Mattermost-адаптер Hermes уже держит исходящий WS** к серверу MM
   (`adapter.connect()` → `ws_connect(wss://…/api/v4/websocket)`, строка 620),
   и **обрабатывает WS-события в `_handle_ws_event`** (строка 798).
   Сейчас принимает только `posted` (804) и `reaction_added` (800); всё прочее
   дропается.

2. **Слэш-команды** в сервер-плагине (Go) перехватываются хуком `ExecuteCommand`
   (в SDK: `ExecuteCommandID`). Внешний Request URL не нужен.

3. **Кнопки/меню/диалоги**: клик идёт HTTP POST на `integration.url`, и сервер MM
   резолвит `/plugins/<plugin_id>/suffix` **локально**, доставляя в `ServeHTTP`
   плагина — без интернета, за firewall ок (подтверждено докой + форумом).

4. **Плагин публикует WS-событие юзерам через `PublishWebSocketEvent(event, payload,
   broadcast)`**, где `broadcast` адресует конкретного юзера
   (`model.WebsocketBroadcast{UserId: <bot_user_id>}`) — т.е. **ровно одному боту**,
   по существующему WS-сокету. Плагин физически шлёт событие в MM-ядро, ядро
   раздаёт его тем юзерам-ботам, чей WS подключён.

5. **Slack-прецедент в Hermes**: Slack-адаптер держит Socket Mode (один исходящий
   WS) и обрабатывает весь интерактив поверх него — **14 action/command-хендлеров**
   (block_actions, confirm, feedback, clarify). Это готовый паттерн для MM.

## Схема транспорта

```
                    Интернет (NAT у Hermes замкнут)
┌────────────────────────────── Hermes-хост (дом, за NAT) ──────────────────────────────┐
│  ┌───────────┐   ┌───────────┐   ┌───────────┐   ┌───────────┐                        │
│  │ nika       │   │ mmdev     │   │ lynx  …   │   │ …        │   профили (боты)        │
│  │ profile    │   │ profile   │   │           │   │           │                        │
│  └─────┬─────┘   └─────┬─────┘   └───────────┘   └───────────┘                        │
│        │               │                                                            │
│   Gateway-процесс (адаптер MM): по одному WS на профиль наружу                        │
│        │  _handle_ws_event()  ← новые ветки: hermes_bridge_command / …               │
└───────┼──────────────────────┬────────────────────────────────────────────────────┘
        │                      │
        │  WS (исходящий)      │  REST /posts/… (отправка ответов)
        ▼                      ▼
┌────────────────────────────────────  Mattermost-сервер (VDS, self-hosted)  ──────────┐
│                                                                                      │
│   ┌────────────────── нативный Go-плагин (hermes-bridge) ──────────────┐            │
│   │  ExecuteCommand  ── слэш-инput  ( /new, /model, … dyn реестр )      │            │
│   │  ServeHTTP       ── кнопки/меню/диалоги (/plugins/<id>/…)          │            │
│   │                                                                     │            │
│   │  после приёма входа:                                                │            │
│   │   PublishWebSocketEvent("hermes_bridge_command", payload,           │            │
│   │                        broadcast→ bot_user_id)                      │            │
│   └─────────────────────────────────────────────────────────────────────┘            │
│        ▲  /plugins/<id>/suffix (локально, без интернета)   ▲ Client (мобила/web/desk) │
│        │                                                   │                           │
│   [users тапают /new и кнопки в UI]                        │                           │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

## Потоки

### Слэш-команда
1. Пользователь пишет `/new` → сервер MM вызывает `ExecuteCommand` плагина локально.
2. Плагин (не зная о «ботах», просто по последнему реестру команд) говорит
   «это команда для реестров» → `PublishWebSocketEvent("hermes_bridge_command", …,
   broadcast={UserId: bot_user_id})`.
3. MM-ядро шлёт событие в WS именно этому боту.
4. Hermes-адаптер `_handle_ws_event` → новая ветка кастомного типа → диспетчер
   слэш-обработчиков (существующий `command_handler_table`).
5. Ответ уходит обычной доставкой бота (`/posts`), от `bot_user_id`.

### Кнопка/меню/диалог
1. Hermes шлёт пост с attachment+actions (обычная доставка).
2. Клик → сервер POST на `/plugins/<id>/suffix` локально → `ServeHTTP` плагина.
3. Плагин → `PublishWebSocketEvent(…, broadcast→ bot_user_id)`.
4. Hermes `_handle_ws_event` → ветка интерактива → обработчик (образец: Slack
   `block_actions`/`_handle_approval_action`).
5. Ответ: обычный пост / `update` оригинального поста / эфемерный.

## Маршрутизация между несколькими ботами (не сломается)

- **Один WS на профиль** (уже так). Плагин адресует событие конкретному боту через
  `broadcast.UserId` → событие приходит ровно в один профиль, без гонок.
- Общий реестр команд/конфиг живёт **на Hermes-хосте** (один YAML); плагин —
  тупой приёмник реестра, «владельца-бота» не имеет и не трогает настройку.
- Маршрутизация «чей канал → кто отвечает» — **на Hermes-стороне** (по `channel_id`/
  `bot_user_id`), как Slack-адаптер не знает про других ботов.

## ЭТАП 2 — ПРОТОКОЛ (дизайн, обсуждение)

### Как ложится в существующий код

Адаптер MM (`_handle_ws_event`, adapter.py:798) читает:
- `evt_kind = event["event"]` — тип события;
- `data = event["data"]` — payload dict (для `posted` там же `data["post"]` = JSON).

Сейчас принимает только `posted` (804) и `reaction_added` (800). Кастомное событие от
плагина = **новая ветка** `if evt_kind == "<наше>"` → разбор `data` → сборка `MessageEvent`
(та же модель, что для posted) → `handle_message`. Никакого нового транспортного пути.

### Типы WS-событий от плагина (event → payload)

Плагин публикует через `PublishWebSocketEvent(name, data, broadcast{UserId: bot})`.
Имя события выбираем по имени реестра бота, чтобы несколько ботов не пересекались
лучше адресуются broadcast'ом, а не фильтром на хосте.

1. **`hermes_bridge_command`** — пользователь вызвал слэш-команду.
   ```
   data = {
     "trigger": "new",            # голая команда (без слэша), из реестра
     "args": "brief",             # всё после команды, строка
     "channel_id": "…",
     "channel_type": "D"|"O"|"G",
     "user_id": "…",              # кто вызвал
     "user_name": "…",
     "thread_id": "…|null",       # если выполнялось в треде
     "response_url": "http://…"   # для отложенного ответа (5 шт/30мин)
   }
   ```

2. **`hermes_bridge_interact`** — клик кнопки/меню/диалога.
   ```
   data = {
     "post_id": "…",              # пост с attachment
     "action_id": "approve",      # id из attachment.actions[].id
     "action_type": "button"|"select"|"dialog",
     "context": {…},              # произвольные props из integration.context
     "channel_id": "…",
     "user_id": "…",
     "thread_id": "…|null",
     "response_url": "…"          # для update оригинального поста / эфемер
   }
   ```

Оба → на Hermes-хосте складываются в `MessageEvent` (тип `.COMMAND` / `.TEXT`),
диспетчер решает по `channel_id`+`user_id`, какой профиль отвечает.

### Реестр команд: Hermes → плагин (конфигурация, а не код)

Плагин НЕ знает команд жёстко — получает реестр от Hermes и регистрирует на сервере.
Канал реестра: отдельное WS-сообщение **от Hermes до MM** (по тому же сокету или по
REST). Выбор — открытый вопрос этапа.

Формат реестра (условно, единый список для плагина):
```
[{trigger, hint, description, autocomplete: true, method: "P"|"G",
  username, icon_url}, …]
```
Плагин на upload/приёме реестра вызывает серверное API регистрации команд
(`RegisterCommand`) → автокомплит-меню видно на мобильном. Новые команды = Hermes
переслал реестр → плагин перерегистрировал, **без пересборки Go**.

### Маршрутизация (кто отвечает)

- Плагин адресует событие конкретному боту через `broadcast.UserId` — гонок нет.
- Hermes-хост по `channel_id` раскладывает на профиль, чей это канал (как в
  существующей материальной маршрутизации).
- «Владельца-бота» плагину не требуется.

### Инварианты Hermes (обязательно сохранить, из AGENTS.md)

- prompt-cache не ломать: слэш-вход не мутировать контекст прошлых витков.
- role-alternation: `MessageEvent` от слэша = отдельный юзер-ход, не инжект середины.
- две дверцы-гварда (base-adapter + runner): `hermes_bridge_command` для команд
  управления (`/stop`, `/new`) должен доходить до runner'а, минуя оба.

### Открытые вопросы этапа протокола

- Канал реестра команд: тот же WS (двунаправленный сокет наружу) или REST на
  `/plugins/<id>/config`? WS проще (уже есть), REST стабильнее для больших реестров.
- Единый реестр на хосте vs реестр per-бот (каждый бот объявляет свои команды).
- Поведение, если бот-профиль выключен (событие плагина никому не доставлено).
- Авторизация: кто может вызывать `/stop`/управление — проверить гейты `allowed_users`.

### РЕШЕНО (Иван, 2026-09-05)

1. **Канал реестра = REST.** Hermes → `POST /plugins/<id>/config` (через админ-токен
   Ники). Плагин принимает реестр команд и регистрирует на сервере
   (`RegisterCommand`). Стабильнее WS для больших списков.
2. **Реестр команд = общий** (как у Slack). Команды уже живут в едином
   `_command_handler_table` раннера — общий реестр всего хоста, не per-бот. Slack-
   адаптер их не хранит, только мапит слэш→handler. Плагин зеркалит этот единый реестр.
3. **Очередь событий не нужна.** При выключенном бот-профиле теряются и обычные
   `posted` (нет WS/обработки) — слэш-событие теряется так же. Поведение консистентно
   с существующим, отдельный буфер не добавляем.

### ИНЖЕНЕРНЫЕ ДЕТАЛИ (решила Ника, 2026-09-05)

**REST-эндпоинт плагина `POST /plugins/hermes-bridge/config`:**
- Заголовок `Authorization: Bearer <shared-secret>` (шаред-секрет из настроек плагина;
  его же держит Hermes-конфиг). Плагин сверяет со своим конфигом до обработки.
- Тело: `{ "commands": [{trigger, hint, description, autocomplete}], "replace": true }`.
- Плагин перерегистрирует реестр (replace = полная замена, last-wins — один источник).
- Ответ: `{ "ok": true, "registered": N }` или `{ "error": "…" }` с HTTP 4xx.

**Обработка слэш-события на хосте (обход двух гвардов):**
- `hermes_bridge_command` приходит WS-веткой → собирается в `MessageEvent.COMMAND`.
- Команды управления (`/stop`, `/new`, `/queue`, …) dispatch **inline**, минуя оба
  гварда: base-adapter `_pending_messages` (по `session_key` в `_active_sessions`) и
  runner-interception. Финальный вызов — напрямую в runner, НЕ через
  `_process_message_background()` (гонка session-lifecycle). Образец запрета — AGENTS.md
  gateway (`command bypass BOTH guards`).
- Обычные (не управляющие) слэш-команды идут штатным путём в `handle_message`.

**Защита управляющих команд:** гейт `allowed_users` (кто может вызвать `/stop`, `/new`)
проверяется на хосте по `user_id` из payload, до диспетчера.

## Границы / открытые вопросы

- Где живёт «реестр команд» и кто его пушит плагину (этап протокола).
- Кастомное WS-событие должно не ломать prompt-cache / role-alternation —
  отдельная проверка при реализации (в AGENTS.md это инвариант).
- Обратный канал «один WS на бот» означает: у каждого бота свой реестр тех
  команд, которые он сам объявил. Ложь/дубль при пересечении каналов — проверить.
- Плагин физически раздаёт события тем, чей WS подключён (ботов). Если бот-профиль
  выключен — событие теряется (не стоит очередь). Приемлемо для MVP? — решить.

## Компоненты для реализации (позже)

1. Go-плагин `hermes-bridge` (VDS, ставится 1 раз): ExecuteCommand + ServeHTTP +
   PublishWebSocketEvent + приём реестра команд.
2. Форк-адаптер MM: ветки `_handle_ws_event` для кастомных типов + диспетчер.
3. Hermes: реестр команд (config.yaml), протокол плагин↔Hermes.
4. Тесты: модель из Slack (action-хендлеры) на MM-пути.
